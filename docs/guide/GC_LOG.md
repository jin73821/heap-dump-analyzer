## GC 로그 (2026-09-14)

세 번째 분석 대상. 흐름: Servers 스캔(`scan_gclog` + `gc_log_path`, 글롭 상수 `RemoteDumpService.GC_LOG_NAME_GLOBS`) → 전송(`gclog.directory=/opt/gclogs/dumpfiles`, `dump_transfer_log.file_type='gclog'`, JVM 수집 재사용) → `gc_log_analysis` 등록 → 분석(`GcLogEngine`, 자체 executor + `GET /api/gc-log/{fn}/status` 폴링) → 요약 컬럼 + `gc_log_result_detail.result_json`(≤4MB) → 덤프 자동 매칭. 업로드는 `/gc-log`(첫 64KB `sniff` 로 형식 판별, 비-GC 로그 400) 또는 대시보드·Files 큐(`isGcLogFilename` 이름 규칙 → 이름이 안 맞으면 앞 64KB **내용 판별** `looksLikeGcLogText` — 서버 `GcLogFormatDetector` 와 같은 정규식이어야 한다, `GcLogTemplateSmokeTest` 가 리터럴을 뽑아 대조).
- **형식:** JDK 9+ 통합 로깅은 데코레이션이 **부분집합·순서 고정**이라 그룹을 내용으로 분류하고 마지막 그룹을 태그로 본다. JDK 8 은 이벤트가 여러 줄(`PrintTenuringDistribution`·G1 트레일러)이라 **대괄호 깊이**로 경계를 잡는다. **JDK 6/7(PermGen·원인 괄호 없음 — JEUS 8 운영 로그)도 JDK8 파서가 읽는다**(함정 55). 두 파서 모두 이벤트를 sink 로 흘리고 보관하지 않는다(대용량 상수 메모리).
- **매칭 규약(`GcLogMatchService.decide`):** 서버 1점 · 시간(absolute 1 / mtime 0.5 / none 0, tol=`gclog.match.tolerance-min`) · 경로 1점(덤프 JVM 후보의 `-Xlog`/`-Xloggc` 경로 == 로그 원격 경로, 회전 접미사·`%t` 무시) → **≥2점이 정확히 1건일 때만 auto**. `manual` 은 연결·해제 모두 자동이 덮지 않는다(`/rematch` 만 예외). 트리거 3곳(전송/업로드·GC 분석 완료·힙 `saveAnalysisToDb` → `HeapAnalysisSavedEvent`).
- **설정 `gclog.*` 9키는 `@Value` 전용**(런타임 변경 없음, 5-place 미적용) — 바꾸면 재기동. k8s 는 `/data/heapdumps/gclogs`(heapdumps PVC 하위). 자동 묶기 4키(`gclog.group.{enabled,max-overlap-seconds,max-gap-minutes,gz-tail-max-bytes}`)는 2026-09-21 추가.
- LLM: `callLlmAnalysis(prompt, systemPrompt)` 오버로드로 GC 전용 시스템 프롬프트, 키 `__gclog__:{fn}`. 힙 AI 프롬프트에는 매칭된 로그의 `== GC 로그 요약 ==` 이 OOM 블록 자리에 주입되고 응답 `gcAdvice` 를 별도 카드로 보인다.
- **'인스턴스' 알약(2026-09-14 KPI 카드 → 2026-09-16 헤더 메타 알약, 서버 알약 오른쪽):** 결과 유무와 무관하게 서버 렌더되고(`#gclInstItem`·`#gclInstValue`·출처 배지 `#gclInstSrc` 덤프/수동·연필 `#gclInstEdit`), 편집 줄은 서버 알약과 같은 `.gcl-meta-form` 이다 — 분석 전·실패 화면에서도 입력할 수 있다. 값 = **수동 입력(`gc_log_analysis.instance_name`) > 연결된 힙 덤프의 Instance**(`HeapDumpAnalyzerService.getEffectiveJeusInstance` — analyze Instance 칩과 같은 규칙: 덤프 수동값 > `jeus.server.name` → `weblogic.Name`). ⚠ 덤프 값은 **복사하지 않고 조회 시점에 읽는다** — 연결을 바꾸거나 해제하면 카드도 따라가야 한다. 그래서 `/match`·`/rematch` 응답(`matchView`)에 `instance` 뷰가 함께 실리고 JS `renderMatchChip` 이 카드도 다시 그린다. 수동 저장은 `POST /api/gc-log/{fn}/instance {instance}`(빈 값 = 수동값 삭제 → 덤프 값 폴백, 키 없음 400, 감사 `[GcLog] action=instance`). 해석은 `GcLogInstanceService`(순수 `view(manual, dumpFilename, dumpInstance)`) — ⚠ **컨트롤러만 주입**할 것(GC 서비스에 넣으면 `HeapDumpAnalyzerService` 경유 순환). 회귀 방어 `GcLogInstanceServiceTest`(4)·`GcLogInstanceEndpointTest`(3)·`GcLogTemplateSmokeTest`.
- **AI 분석 카드(2026-09-14):** 상단 `AI 분석`·카드 `분석/재분석` 버튼은 **확인 모달(`#aiConfirmModal`)만 연다** — LLM 요청은 `confirmAi → startAi` 에서만 나간다(새 트리거도 `runAi()` 경유). 분석 중에는 초 단위 경과 시간을 보이고, 실패 시 오류를 위에 얹고 직전 결과(`_aiHtml`)를 유지한다. ⚠ 이 페이지의 카드·소견에 **좌측 색 띠(`border-left`/inset shadow)를 쓰지 말 것**(사용자 요청으로 제거 — 심각도는 옅은 배경 + 같은 계열 1px 테두리 + 배지). `GcLogTemplateSmokeTest` 가 `gc-log.css` 의 `border-left` 부재를 단언한다.
- **결과 페이지의 자동 시작 규약:** 미분석(NOT_ANALYZED)은 열면 시작, **실패(ERROR)는 `?start=1` 이 있을 때만 시작**(확인 모달 `AnalyzeConfirm` 의 gclog 이동 경로가 붙이고, 페이지가 `replaceState` 로 즉시 지운다). 표시 없이 실패 기록을 열면 오류 + '다시 분석' 버튼만 보인다. ⚠ 이 표시를 빼면 실패 행에서 '분석'을 눌러도 요청이 나가지 않고 **옛 오류 문구만 다시 보여** 수정이 배포돼도 계속 같은 오류로 보인다(2026-09-14 실제 제보 — 접근 로그에 POST 가 없는 것으로 확정).
- **누수 추세(`trend`)는 기동 후 300초 이내 점을 빼고, 남은 점이 600초 미만 폭이면 기울기를 내지 않는다**(`GcLogAnalyzer.WARMUP_SEC`/`MIN_TREND_SPAN_SEC`, 이유는 `trend.note`). 몇 초 구간의 증가를 시간 단위로 환산하면 수만 MB/h 같은 허수가 나온다 — 2026-09-14 정상 Spring 기동 로그가 '+40,390 MB/h 누수 의심' 으로 나왔다. 차트용 `afterPoints` 는 전체, 회귀 점 수는 `pointsUsed`.
- **대시보드 Recent Files = 힙 저장소 + GC 로그 저장소(2026-09-14, `RecentFileItem`):** 종전엔 힙 저장소(`listFiles`)만 나열해, 힙 저장소에 사본이 남은 `gc.log` 가 GC 쪽에서 분석이 끝났는데도 '미분석' + 힙 분석 버튼으로 보였다(대시보드에서 올린 GC 로그는 아예 목록에 없었다). 항목의 `kind`(heap|gclog)가 상태·버튼 경로를 정한다 — GC 는 `/gc-log/analyze`(미분석 폴백 `?start=1`)·`/api/gc-log/download`·`DELETE /api/gc-log?deleteFile=true`. ⚠ `RecentFileItem.merge` 는 **힙 쪽 분석 기록이 없고 이름·크기가 GC 로그 파일과 같은** 힙 항목을 사본으로 보고 목록에서 뺀다(파일은 그대로 — Files 페이지에는 남는다). 크기가 다르거나 힙에서 분석한 파일은 둘 다 남긴다. 대시보드 통계(FILES·DISK·Analyzed)와 `files` 모델은 여전히 힙 저장소 기준이고, 목록 헤더 건수만 `recentCount`. 힙 MAT 큐 폴링(`applyInProgress`)은 `data-kind="gclog"` 항목을 건너뛴다. 회귀 방어 `RecentFileItemTest`(4)·`DashboardDetectSummaryTest.recentFilesRenderGcLogWithGcRoutes`.
- **출처 서버명(2026-09-15):** 결과 페이지 헤더의 `서버` 알약은 **값이 없어도 `미지정` + 연필로 항상 렌더**한다 — `th:if` 로 숨기면 업로드 때 비운 로그는 나중에 입력할 곳이 없다(실제 제보). 저장 `POST /api/gc-log/{fn}/hostname {hostname}`(빈 값 = 삭제, 키 없음 400)은 서버명이 매칭 신호라 재평가 후 **매칭 뷰 + `hostname`** 을 돌려주고 JS 가 `renderMatchChip` 으로 칩·인스턴스 카드를 함께 갱신한다. 회귀 방어 `GcLogHostnameEndpointTest`(2)·`GcLogTemplateSmokeTest`.

- **파일 분류 'GC로그' = 저장소 이동(함정 53):** 분류 라벨(`file-classifications.properties`)은 이름표지만 GC 로그 분석기는 GC 저장소 파일만 읽는다. `classifyFile` 이 `adoptFile`(→GC, 형식 sniff·충돌 검사, NOT_ANALYZED 재시작) / `releaseFile`(GC→힙덤프 저장소, 결과·AI·엔티티 삭제)을 부르고, 분석 결과가 있거나 분석 중인 힙·코어 파일은 거부한다. 저장소 간 조정은 **컨트롤러**에 둔다(서비스끼리 주입하면 `GcLogAnalyzerService → HeapDumpAnalyzerService → JvmHeapInfoService → RemoteDumpService → GcLogAnalyzerService` 순환으로 기동 실패).

- **압박 Full GC 분류(2026-09-16, 함정 58):** Full GC 를 `FullGcKind` 5종으로 나눈다 — 첫 일치 우선 `EXPLICIT` → `METASPACE` → `GC_LOCKER` → `HEAP_PRESSURE`(Allocation Failure·Ergonomics·승격 실패·CMF·to-space·**JDK 6/7 무원인**·Degenerated) → `OTHER`. 원인 어휘는 `GcLogSupport.isPressureCause`(`isExplicitCause` 옆 — 새 원인은 여기만). 집계는 `GcLogResult.fullGcSummary`(종류별 수·압박 원인 분포·회수율 min/중앙값·20% 미만 수·직후 점유율·간격 앞/뒤 절반 중앙값·차트 점 ≤500·최저 회수 5건) — **명시적 Full 은 회수율 표본에서 제외**. 소견 `FULL_GC_LOW_RECLAIM`(압박 ≥2 · 회수율 <20% ≥2 → 마지막 직후 최대 힙 대비 ≥85% Critical / ≥60% High / Medium)·`FULL_GC_INTERVAL_SHRINKING`(간격 ≥6 · 뒤 절반 ≤ 앞 절반 ×0.5 → ×0.25 또는 5분 미만이면 High). ⚠ **`pressureFullGcPerHour` 는 여전히 비명시 Full/h** — FREQUENT 임계·JS 경고색 폴백·힙 패널이 의존하니 뜻을 바꾸지 말 것(배너·KPI·`gc_log_analysis.pressure_full_gc_count` 는 HEAP_PRESSURE 전용). 결과 페이지 최상단 배너 `#gclPressureBanner` 는 상태 5종(압박/힙 압박 아님/전부 명시적/옛 결과→재분석 버튼/Full 없음)이고 `해당 이벤트 보기` 는 유형 FULL + 검색 '압박' 으로 기존 `applyFilter` 술어를 재사용한다(detach 표). 차트 ▲ 는 Series 가 아니라 블록의 점(Series 는 병합 시 유형이 FULL 로 뭉개져 압박/명시적을 못 가른다). AI 프롬프트 `== Full GC 분류 ==` 섹션 + `GcAiResponseNormalizer`(severity 4값·recommendations 리스트·길이 상한·`warnings`). **엔티티 컬럼은 `forgetAnalysis` 에서도 지울 것.** 회귀 방어 `GcLogPressureFixtureTest`(합성 픽스처 — `GcLogTestSupport.pressureParallelLog()` 와 동일성 고정, `-Dgclog.fixture.write=true` 로 재생성)·`GcAiResponseNormalizerTest`·`GcLogAiPromptTest`.
- **명시적 GC·누수 실질성(2026-09-15, 함정 57):** `systemGcCount` 는 호출 수(Parallel Young+Full 짝), `FULL_GC_FREQUENT` 는 `pressureFullGcPerHour`(명시적 Full 제외), `LEAK_TREND` 는 `trend.significant`(증가량 ≥ max(32MB, 힙 2%) 그리고 90% 도달 ≤ 30일)일 때만, `SYSTEM_GC` 는 영향 기준 심각도 + 규칙 간격(1시간 = RMI) + 수집기 맞춤 권고. 실측 픽스처 `src/test/resources/gclog/spdomain-jdk8-parallel-heapatgc.log.gz`(`GcLogRealLogRegressionTest`) — **판정 규칙을 바꾸면 이 파일이 종합 Low·SYSTEM_GC 1건으로 남는지 먼저 볼 것.**
- **회전 로그 이어붙이기(2026-09-20, 함정 60~64):** 회전본 여러 개를 시간순으로 이어 붙여 한 번에 분석한다. 결과는 **대표 행**(사용자가 연 로그)의 `gc_log_analysis` 에 저장하고 구성은 `member_files`(병합 순서 JSON, 대표 포함)·`member_count`·`members_bytes`·멤버 쪽 역참조 `part_of` 로 표시한다 — `{filename}` 엔드포인트가 전부 그대로 동작한다. 엔진은 `GcLogEngine.analyze(List<GcLogSource>, …)` 오버로드(조각마다 gz 판정·형식 sniff·**파서 교체**, 전역 줄 번호·이벤트 예산·seq)이고 결과에 `segments`(조각별 줄 범위·시각·실행 번호·원문 30줄)가 실린다(`SCHEMA=2`, ⚠ **단일 파일이면 `segments==null` 이고 결과 JSON 이 종전과 완전히 같아야 한다** — `GcLogMultiSourceEngineTest.singleSourceJsonIsIdenticalToLegacyPath` 가 안전벨트). 50. **통합 로깅의 `gc,cpu` 줄은 완료 줄 뒤에 오고, concurrent 사이클은 pause 와 GC(n) 을 공유한다 (2026-09-14)** — JDK 21 실측 순서 `gc,start → gc,heap → gc,metaspace → gc(완료 ms) → gc,cpu` 이고 그 사이에 다른 id 의 `Concurrent Mark Cycle` 시작 줄이 끼어든다. 완료 즉시 내보내면 cpu 가 빠지므로 `pending` 에 들고 있다가 다음 pause 의 start/완료에서 내보낸다(concurrent 시작·완료는 flush 하지 않는다). 55. **JDK 7 이하 GC 로그에는 원인 괄호가 없다 — `[GC` 접두로는 Young·CMS 마킹·전체 수집을 구분할 수 없다 (2026-09-14)** — JDK 8 은 `[GC (CMS Initial Mark)`·`[GC (CMS Final Remark)` 로 찍지만 JDK 6/7 은 `[GC [1 CMS-initial-mark: …]`·`[GC[YG occupancy: … [1 CMS-remark: …]` 이고, **전체 수집도 `[Full GC` 가 아니라 `[GC [ParNew: …][CMS: …]`** 다. 접두·원인으로 판정하면 CMS 로그의 모든 일시정지가 예외 없이 Young 으로 들어가 Full GC 0회·Young 평균 수백 ms 가 되고, 소견은 Medium 에 그친다(JEUS 8 운영 로그 실측 — "JVM 1.8.0" 이라고 전달됐지만 `CMS Perm` 이 있어 JDK 7 이하였다). 그래서 CMS 유형은 **본문 마커**(`CMS-initial-mark:`·`CMS-remark:`)로, 전체 수집은 **`[GC` 안의 Old 세대 라벨**(`CMS`·`Tenured`)로 판정한다 — JDK 8 의 promotion failed·concurrent mode failure 도 이 규칙으로 Full 이다. ⚠ CMS 마킹의 `old(oldCap)] heap(heapCap)` 은 **순간 점유량**이라 힙 before/after 로 넣지 말 것(누수 추세·할당률 오염) — Old 점유량과 용량만 쓰고, 이것이 `CMS_OLD_SATURATED`(사이클 시작 시 Old ≥98% 연속) 소견의 근거다. ⚠ Old 수집 중 동시 단계가 **같은 이벤트 안에 끼어든다**(`[CMS2026-…: [CMS-concurrent-mark: …] [Times: …]` + 다음 줄 ` (concurrent mode failure): …`) — 걷어내지 않으면 `[CMS` 라벨이 끊겨 Old 크기가 힙 총합으로, 안쪽 `[Times:` 가 이벤트 시간으로 잡힌다. 회귀 방어 `Jdk8GcLogParserTest.legacyCms*`·`concurrentPhaseInterleaved*`·`GcLogAnalyzerTest.legacyCms*`.

60. **회전 GC 로그는 이름순이 시간순이 아니다 — `.0` 이 `.2` 보다 뒤일 수 있고 현재 파일은 접미사가 없다 (2026-09-20)** — JDK 9+ 통합 로깅의 `filecount=N` 은 아카이브 슬롯을 **돌려 쓴다**. 이 서버 `logs/` 실측이 `gc.log.0`(9/19 22:18) → `.3`(22:57) → `.4`(23:09) → `.1`(23:23) → `.2`(9/20 10:56) → `gc.log`(현재) 였다 — 이름순으로 이으면 하루가 뒤죽박죽이 되고 간격·추세·차트가 전부 거짓이 된다. JDK 8 `-XX:+UseGCLogFileRotation` 은 반대로 **현재 파일이 `gc.log.<i>.current`** 다. 정렬 기준은 **내용의 첫 절대 시각 → (전부 없으면) 파일 시각 → 첫 uptime** 이고 판정은 `GcLogAnalyzerService.orderMembers` 한 곳이다(순수 함수). ⚠ **파일명·회전 번호로 정렬하는 코드를 만들지 말 것.** ⚠ 전송본의 파일 mtime 은 scp 가 새로 찍으므로 순서 근거가 못 된다 — `peek(file, remoteMtime)` 처럼 **원격 mtime** 을 넘길 것. 실측 픽스처 `src/test/resources/gclog/rotated/*` 와 `GcLogRotatedRealFixtureTest`·`GcLogCombineServiceTest.ordersByFirstTimestampNotRotationNumber` 가 이 배열을 고정한다. 덧붙여 이 환경의 회전본은 전부 `gc,init` 로 시작해 `gc,heap,exit` 로 끝난다 — **회전 = 재기동**이라 여러 실행이 섞인 입력이 예외가 아니라 기본이다.

61. **이어 붙이면 uptime 이 0 으로 되돌아간다 — x 축을 그대로 두면 10분 창·할당률·누수 추세가 조용히 거짓말을 한다 (2026-09-20)** — `GcLogAnalyzer.effectiveX` 는 uptime 을 우선한다. 재기동이 섞인 입력에서는 x 가 `665 → 0.003` 으로 역행해 ① `slideWindow` 의 `while (x - first > 600)` 이 영영 비지 않아 `maxOverheadPct10m` 이 부풀고 ② 할당률은 `x > prevX` 조건에 걸려 구간이 통째로 누락되며 ③ 차트 선이 되돌아 그어진다. **오프셋을 계산하지 말고 기준 자체를 바꾼다** — 조각이 2개 이상이면 절대 시각을 우선(`Meta.xBasis=absolute`, `effectiveX` 에 이미 있던 분기)해 `summaryForDump` 의 `dumpPosition.uptimeSec = firstUptimeSec + (dumpEpoch - logStart)` 가 수정 없이 맞는다. 절대 시각이 없을 때만 조각을 이어 붙이고(`stacked`) **공백을 모른다는 표시(`gapUnknown`)** 를 남긴다. ⚠ `durationSec` 은 `lastX-firstX` 가 아니라 **세그먼트 커버 구간의 합**이다(JVM 이 꺼져 있던 시간을 처리량·Full GC/h 분모에 넣지 않는다). 그 대신 덤프가 로그 범위 안인지는 `Meta.spanSec` 으로 판정한다 — 커버 합으로 판정하면 공백 뒤의 덤프가 "범위 밖"이 되어 힙 패널의 세로선이 사라진다. ⚠ **가장 위험한 것은 누수 오탐이다** — x 기준이 절대 시각으로 바뀌면 `WARMUP_SEC` 필터가 통째로 꺼져 실행마다의 기동 램프가 전부 회귀에 들어간다(2026-09-14 의 `+40,390 MB/h` 오탐, 함정 57 이 구간 수만큼 증폭된 꼴). 워밍업 제외는 **넣을 때 per-run `ev.uptimeSec` 기준**으로 걸고, 회귀는 **가장 긴 실행 안에서만** 돌린다. ⚠ 실행 경계 판정 `RUN_RESTART_SLACK_SEC` 은 **0.5초**다 — 크게 잡으면 기동 직후 회전된 짧은 조각(uptime 0.003~2초)의 재기동을 놓친다.

62. **멤버 경계에서 파서·이벤트 예산·seq 를 이어 쓰면 안 된다 — 이벤트가 합쳐지고 상한이 N배가 되며 표 정렬이 깨진다 (2026-09-20)** — `Jdk8GcLogParser` 는 대괄호 깊이로 경계를 잡아 파일 끝에서 잘린 이벤트에 다음 파일 헤더가 이어지면 **두 이벤트가 하나로 뭉치고**, `UnifiedGcLogParser` 는 재기동 시 `GC(n)` id 가 0부터 다시 시작해 **이전 실행의 열린 id 와 충돌**한다. 그래서 조각마다 파서를 새로 만들고 앞 조각은 `finish()` 로 마감한다(미종결분은 `droppedIncomplete` 로 계수 — 조용히 삼키지 않는다). 다만 새 파서에 **① 전역 이벤트 예산**(`maxEvents` 를 그대로 주면 상한이 조각 수만큼 곱해진다)과 **② 이어지는 `seq`**(0부터 주면 `EventRow.seq` 가 중복돼 이벤트 표 기본 정렬이 뒤섞인다)를 넘긴다 — `new XParser(sink, maxEvents, seqBase)` + `seqEnd()`. 줄 번호는 **전역**이 맞다(`maxAtLine`·`fullGcSummary.lastLine`·원문 샘플이 전부 전역 전제) — 화면에 `gc.log.2:1043` 으로 보이려면 저장은 전역, 표시는 `Segment.firstLine` 으로 환산할 것. ⚠ 조각의 형식 sniff 가 `UNKNOWN` 이라고 전체를 거부하지 말 것 — 헤더 없는 회전본은 흔하다. **알려진 형식끼리 불일치할 때만 거부**하고 UNKNOWN 은 그룹 형식을 물려받는다(`formatInferred`). ⚠ `flagged(2000)`·`head/tail(2500)` 은 **선착순**이라 앞 조각이 독식하면 마지막 파일의 Full GC 가 표에 한 줄도 안 남는다 — 조각이 2개 이상이면 **세그먼트별 쿼터**로 나눈다("범위를 넓혔는데 최근 구간이 안 보이는" 역효과 방지).

63. **이어 붙인 결과는 대표 행에 얹되 `file_size` 만은 대표 파일 자신의 크기여야 한다 — 합계를 쓰면 다음 목록 조회가 자기 결과를 지운다 (2026-09-20)** — 그룹 결과를 별도 행이 아니라 사용자가 연 로그의 `gc_log_analysis` 행에 저장하면 `{filename}` 엔드포인트 19개·Files·대시보드·현황판·AI 인사이트 키가 전부 그대로 동작한다(별도 그룹 엔티티는 filename=키 규약을 전역에서 이중화해야 해 기각). 그런데 `listExistingFiles` 는 **크기가 기록과 다르면 다른 파일로 보고 `forgetAnalysis`** 한다(함정 54) — `file_size` 에 멤버 합계를 넣으면 다음 화면 진입에서 결과·AI·매칭이 **오류 없이 사라진다**. 합계는 `members_bytes` 에 따로 둔다. ⚠ 멤버 쪽에는 역참조 `part_of` 를 둘 것 — 없으면 `gc.log.0~.4` 가 목록·현황판에 미분석 행으로 남아 사용자가 같은 파일을 또 분석한다(현황판은 `part_of != null` 을 아예 건너뛴다). ⚠ **`forgetAnalysis` 에 `member_files`·`member_count`·`members_bytes` 와 멤버 쪽 `part_of` 해제를 반드시 넣을 것** — 같은 이름으로 새 파일이 들어온 뒤 재분석하면 **옛 구성 그대로 엉뚱한 파일과 합쳐 분석**한다. ⚠ 멤버가 삭제·분류 이동돼도 **파일은 건드리지 않고 DB 참조만** 끊는다(함정 53 — 형제 회전본 보존). 회귀 방어 `GcLogCombineServiceTest`(11).

64. **로그 범위를 넓히면 덤프 자동 매칭이 ambiguous 로 조용히 풀린다 — 매칭 시간창은 대표 구간만 쓸 것 (2026-09-20)** — `GcLogMatchService.timeScore` 는 `logStart-tol ≤ dumpTs ≤ logEnd+tol` 이면 1점이고 서버 1점을 더해 2점이면 strong 이다. 범위가 13시간으로 넓어지면 그 안의 덤프가 전부 strong 이 되어 `strong.size()>1` → `ambiguous:N`, 그리고 `apply()` 가 **기존 `matched_dump_filename` 을 null 로 덮는다**(manual 만 보호). 즉 잘 붙어 있던 자동 연결이 이어붙이기 재분석 한 번에 사라진다. 그래서 화면용 `log_start/log_end`(전체 범위)와 **매칭용 `match_window_start/end`(대표 파일 자신의 구간, `applySummary` 가 `segments` 에서 뽑는다)를 분리**했다 — `logFacts()` 만 후자를 쓰므로 매칭 동작이 이어붙이기 전후로 불변이고 `GcLogMatchServiceTest` 7건이 무수정으로 통과한다.

66. **분석명(`호스트네임_인스턴스명_일자`)은 표시용이고 키는 여전히 파일명이다 — 일자는 분석이 끝나야 확정된다 (2026-09-20)** — `gc_log_analysis.analysis_name` 은 목록·제목에 보이는 이름일 뿐 어떤 조회에도 쓰이지 않는다(unique 제약도 없다 — 겹치면 `_2` 가 붙는다). 규칙의 단일 출처는 `GcLogNameService.build(host, instance, start, end)` 이고 재계산 시점은 **등록·분석 성공·호스트네임/인스턴스 변경·이어붙이기** 네 곳이다. ⚠ 일자는 **로그 시작일**이라 분석 전에는 전송 mtime·등록 시각으로 잠정 표기하고 분석이 끝나면 바뀐다 — 이름이 바뀌는 것이 정상이니 이름으로 무언가를 찾는 코드를 만들지 말 것. ⚠ 자정을 넘는 로그는 시작일 한 건으로 두고(파일을 쪼개면 원문·줄 번호 대조가 깨진다) 이어 붙여 여러 날에 걸칠 때만 `20260919-0920` 범위 표기가 된다. ⚠ **수동 업로드는 호스트네임이 필수**다 — 분석 시작 초크포인트는 `GcLogAnalyzerService.requireHostname` 하나이고(`MissingHostnameException` → 컨트롤러가 400 `NO_HOSTNAME`), 프런트(업로드 폼·`AnalyzeConfirm`)는 그걸 먼저 알려 줄 뿐이다. 전송본은 `registerTransferred` 가 서버명과 `jvm_info` 마커(`WasInstanceName.resolve`)로 둘 다 자동으로 채운다.

67. **연속 로그 자동 묶기 — 겹침이 유일한 강한 부정 신호이고, 마커 부재는 불일치가 아니다 (2026-09-21)** — 업로드한 회전본을 자동으로 묶을 때 가장 나쁜 실패는 "안 묶이는 것"이 아니라 **다른 JVM 의 로그를 조용히 한 묶음으로 만드는 것**이다. 두 노드(was01-a/b)의 로그를 함께 올리면 **시작 시각만 보면 완벽히 연속**으로 늘어서므로, 끝 시각을 읽어 겹침을 봐야 한다(평문은 꼬리 256KB 역스캔이라 파일 크기와 무관, gz 는 `gclog.group.gz-tail-max-bytes` 이하일 때만). ⚠ **mtime 을 끝 시각 대용으로 쓰지 말 것** — 업로드본의 로컬 mtime 은 업로드 시각이다(`fallbackEndEpochSec` 이 같은 이유로 거부한다). 끝 시각을 모르면 **그 경계에서 끊는다**(안전측). 반대로 ⚠ **마커가 없는 것을 불일치로 처리하지 말 것** — JDK 9+ `filecount` 회전은 `gc,init` 을 첫 파일에만 쓰므로 헤더 없는 회전본이 정상이다. 축 판정을 3값(`MATCH`/`MISMATCH`/`UNKNOWN`)으로 두고 **양쪽 모두 값이 있을 때만** 비교한다. `jdkVersion` 은 차단 마커가 아니다(빌드 문자열이 패치 하나로 바뀌는데 회전 = 재기동이라 정상) — 경고만. ⚠ **공백 임계는 넉넉해야 한다**(기본 12시간) — 회전 = 재기동인 환경에서는 파일 사이에 JVM 정지 시간이 실제로 들어가므로 30분 같은 값이면 정상 세트가 조각마다 따로 논다. ⚠ **묶기는 분석이 아니다** — `linkCombined` 는 호스트네임을 요구하지 않고(분석 초크포인트는 `requireHostname` 하나, 함정 66) 자동 경로는 `submitAnalysis` 를 절대 부르지 않는다(`GcLogGroupEndpointTest` 가 `verify(never())` 로 고정). ⚠ **구성을 바꾼 뒤 `forgetAnalysis` 를 부르지 말 것** — 마지막 줄의 `clearMemberLinks` 가 방금 건 링크를 되돌리고 서버명·인스턴스명까지 날린다. 결과만 버리는 `invalidateResult`(출처·구성·`file_size`·덤프 매칭 보존)를 쓴다. 곁들여 고친 두 구멍 — `forgetAnalysis` 가 **자기 `part_of` 를 지우지 않아** 멤버였던 파일을 같은 이름으로 재업로드하면 새 내용이 옛 묶음에 매달렸고, `memberFilesOf` 가 **존재만 확인**해 `MemberRef.size` 스냅샷을 아무도 읽지 않았다(지금은 크기가 다르면 이름을 밝히고 거부한다). 회귀 방어 `GcLogGroupPlannerTest`(16)·`GcLogAutoGroupRealFixtureTest`(7, 실측 회전본 6개)·`GcLogGroupLinkServiceTest`(12)·`GcLogGroupEndpointTest`(7)·`GcLogDrawerTemplateSmokeTest`(12)·`GcLogSideDrawerModelTest`(3)·`UploadQueueGcOriginTest`(8).

68. **연속 로그 제안의 후보는 "같은 서버"만으로 고르면 안 되고, 분석된 행의 `log_end` 는 그 파일의 끝이 아니다 (2026-09-23)** — ① 한 서버의 인스턴스별 로그(`/logs/was1/gc.log`·`/logs/was2/gc.log`)를 한 사슬에 넣으면 시간순으로 번갈아 놓여, planner 가 한 인스턴스의 끝과 다른 인스턴스의 시작을 "연속" 으로 이을 수 있다(인스턴스명이 비어 있으면 출처 축도 못 막는다). 그래서 `seriesKey` 로 **회전 계열을 먼저 나눈다** — 원격 경로 우선(전송 회피명 `gc.log_202609231516.3` 은 파일명 base 를 망가뜨린다), 회전 접미사·`%t`·4자리 이상 숫자(pid·epoch)만 가리고 ⚠ **디렉토리와 짧은 숫자는 가리지 말 것**(`gc_container1.log`/`gc_container2.log` 는 다른 인스턴스다). ② `gc_log_analysis.log_end` 는 마지막 **GC 이벤트** 시각이라 JVM 종료 줄(`gc,heap,exit`)보다 몇 분 이르다 — 지문 끝 시각으로 쓰면 이어지는 회전본 사이에 없는 공백이 생긴다(실측 13:18:02 vs 13:22:36). `probe()` 는 평문이면 꼬리 256KB 를 먼저 읽는다. ⚠ **이어 붙인 대표의 `log_end` 는 묶음 전체의 끝**이라 그 파일의 끝으로 쓰면 겹침(=다른 JVM)으로 오판된다. ③ 제안은 **읽기 전용**이다 — 묶기는 사용자가 수락했을 때 `/combine` 이 한다(`GcLogGroupSuggestionTest` 가 `save` 0회를 단언). ④ 확인 창은 판정이 끝날 때까지 시작 버튼을 잠근다 — 열자마자 Enter 를 누르면 단독 분석으로 새기 때문이다. 대신 판정이 멈춰도 분석이 막히지 않게 8초 뒤 단독 분석을 풀어 준다.
