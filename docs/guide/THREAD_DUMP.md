# 스레드 덤프

> 2026-11-26 v2.7.0 에서 추가한 네 번째 분석 대상의 규약·함정이다(v2.7.1 힙 덤프 연계·이어 붙이기 포함). 경로는 저장소 루트 기준이고, 함정 번호는 소스 주석이 참조하는 전체 공통 번호다.

## 스레드 덤프 (2026-11-26)

HotSpot 계열 JVM 의 `jstack` · `kill -3` · `jcmd Thread.print` 출력을 분석한다. 서버 stdout 로그에 섞인 덤프와 `.gz` 도 받는다. IBM J9 javacore 와 `jcmd Thread.dump_to_file` 은 **미지원**이며 "스레드 덤프 아님" 과 구분해 `UNSUPPORTED_FORMAT` 으로 안내한다.

흐름: 업로드(`/thread-dump` · 대시보드·Files 큐) → `threaddump.directory=/opt/threaddumps/dumpfiles` → `thread_dump_analysis` 등록 → 분석(`ThreadDumpEngine`, 자체 실행기 1스레드 + `GET /api/thread-dump/{fn}/status` 폴링) → 요약 컬럼 + `thread_dump_result_detail.result_json`(≤4MB) → 결과 화면·PDF·AI.

- **범주 id 는 전 계층에서 `threaddump`** — Files `data-file-type`, 업로드 큐 모드·유형, 분류 값, `AnalyzeConfirm` kind, `AnalysisHistoryItem.fileType`. 표시명 "스레드 덤프"(Files 탭은 `Thread Dump`), 순번 접두 `T`, 배지 `THREAD`(하늘색 `#E0F2FE`/`#075985`).
- **통합 범위는 최소다:** Files 탭·업로드 자동 분류·분류 모달 + 전용 메뉴(`#gbNavThreadDump`)와 화면. 대시보드 Recent Files·탐지 카드, 현황판 도메인, 서버 스캔 원격 수집, 힙 덤프 매칭에는 **넣지 않았다**. 대시보드에서 스레드 덤프만 올리면 `onUploadQueueDone` 이 `/thread-dump?file=` 로 보낸다(목록에 안 나오는 파일이 사라져 보이지 않게).
- **설정 `threaddump.*` 6키는 `@Value` 전용**(런타임 변경 없음, 5-place 미적용 — `gclog.*` 와 같은 정책): `directory` · `max-file-bytes`(1GB, gz 는 해제 후) · `max-line-chars`(4096) · `max-threads-per-snapshot`(20000) · `max-snapshots`(30) · `analysis.timeout-minutes`(10). k8s 는 `/data/heapdumps/threaddumps`(heapdumps PVC 하위)로 둘 것 — `DEPLOYMENT.md`.
- **자동 분류 — 브라우저 규칙 = 서버 규칙.** `upload-queue.js` 의 `_TD_NAME_RE`·`_TD_HEADER`·`_TD_THREAD`·`_TD_STATE` 는 `ThreadDumpFormatDetector` 의 `NAME_RE`·`HEADER_RE`·`THREAD_RE`·`STATE_RE` 와 **글자 그대로 같아야** 한다(`ThreadDumpUploadContractTest` 가 대조). 양성 조건은 `(헤더 그리고 스레드 줄 ≥1) 또는 (스레드 줄 ≥3 그리고 상태 줄 ≥1)`.
  - `resolveFileType`(auto) 순서: 코어 이름 → **스레드 덤프 내용** → 힙 확장자 → GC 이름 → **스레드 덤프 이름** → GC 내용 → 확장자 없음 → heapdump.
  - **이름 규칙**은 `thread_dump`·`threaddump`·`tdump`·`jstack`·`stack_dump` 와 **`thread`(2026-11-27 추가 — `threads`, 숫자가 바로 붙은 `thread1` 포함)** 가 구분자(`-` `_` `.` 또는 처음·끝)로 떨어진 낱말일 때다. 예: `thread.txt` · `was1_thread_20261127.log` · `thread1.out`. `mythread.log` · `threadpool.xml` 처럼 낱말 안에 든 thread 는 맞지 않는다. ⚠ 이름만 맞고 덤프가 없는 파일(`thread_pool.xml` 등)은 스레드 덤프로 분류돼 서버가 `NOT_THREAD_DUMP` 로 거부한다 — 그런 파일은 Files 의 해당 유형 탭에서 올린다. `threads.hprof` 같은 힙 확장자는 순서상 힙 확장자가 앞이라, 내용에 덤프가 없으면 힙 덤프로 남는다.
  - 브라우저는 앞 64KB 와 **뒤 64KB** 를 읽는다(`kill -3` 덤프는 로그 끝에 붙는다). GC 이름 규칙에 맞는 파일과 `.gz` 는 읽지 않는다.
  - ⚠ GC 줄과 덤프가 함께 든 stdout 은 `threaddump` 로 분류된다(2.6.2 까지는 `gclog`). 마커가 더 특정적이어서다.
  - 앞뒤 64KB 에 덤프가 없는 큰 로그는 자동 판별되지 않는다 → Files `Thread Dump` 탭(모드 강제)·`/thread-dump` 업로드·분류 모달로 넣는다. **서버는 전용 업로드와 분류 편입 때 파일 전체를 스트리밍 스캔**한다(`ThreadDumpFormatDetector.scan`, 첫 양성에서 종료).
- **업로드는 `tmp/<uuid>.part` 에 받아 판별한 뒤에만 `dumpfiles/` 로 옮긴다**(`storeUpload`). 전송 중인 부분 파일이 목록에 보이거나 거부된 파일의 유령 기록이 남지 않는다. 덮어쓰지 않는다(같은 이름 409 `DUPLICATE_NAME`).
- **분류 = 저장소 이동**(`HeapFileApiController.classifyFile`): "대상 저장소가 편입(형식 검사 → 이동 → 등록)하고 원 저장소는 기록만 정리" 로 통일했다. 형식 검사가 이동보다 먼저라 거부되면 파일은 제자리에 있다. gclog ↔ threaddump 는 힙 저장소를 거치지 않는다(`adoptFile` + 상대의 `forgetMovedFile`). 저장소가 넷이라 요청 body 의 `from`(현재 유형)으로 출처를 정하고, 없으면 "정확히 한 저장소" 일 때만 옮긴다(아니면 409). 서비스끼리 주입하지 않는다(기동 순환 — `GC_LOG.md`). `ThreadDumpAnalyzerService` 는 컨트롤러에 **선택 주입 필드**다(3-인자 생성자를 쓰는 테스트 보존).
- **파서·분석기**(`parser/threaddump/*`, 스프링 의존 없음): `ThreadDumpEngine.LineReader`(상한 있는 줄 리더·정리) → `ThreadDumpParser`(줄 상태 기계) → `ThreadDumpAnalyzer`(규칙) → `ThreadDumpResultCodec`.
  - 스냅샷 경계: `Full thread dump … VM (` 줄 ~ `JNI global ref…` 트레일러(+ JVM 데드락 섹션, `kill -3` 의 `Heap` 섹션). 헤더 없는 조각은 스레드가 3개 이상일 때만 스냅샷으로 받는다. 스레드 구간에서 문법 밖 줄이 30줄 이어지면 `INTERRUPTED_BY_LOG` 로 닫고 그 줄들을 잡음으로 되돌린다. `max-snapshots` 를 넘으면 **마지막 N개**를 남긴다.
  - 줄 앞 접두는 k8s CRI(`<ts> stdout F `)·journald 두 형태만 뗀다. 그 밖의 접두는 해석 못 한 줄로 드러낸다.
  - 스택은 `StackTable` 로 사전화한다 — 메모리가 파일 크기가 아니라 서로 다른 스택 수에 비례한다. 프레임의 `module@version/` 접두는 떼고 저장한다.
- **소견 코드**(`Critical|High|Medium|Low|Info`, 종합은 Info 를 뺀 최댓값): `DEADLOCK` · `LOCK_CONTENTION` · `LOCK_OWNER_STUCK` · `BLOCKED_RATIO_HIGH` · `STUCK_THREADS` · **`BUSY_LOOP_SUSPECT`** · `HOT_THREAD_CPU` · `VM_THREAD_CPU_HIGH` · `POOL_NO_IDLE` · `CONN_POOL_WAIT` · `DB_WAIT_CLUSTER` · `REMOTE_CALL_WAIT_CLUSTER` · **`SOCKET_WAIT_CLUSTER`** · **`CONNECT_WAIT`** · `THREAD_COUNT_HIGH` · `THREAD_COUNT_GROWTH` · `EXECUTOR_LEAK_SUSPECT` · `FINALIZER_BLOCKED` · `WLS_STUCK_THREADS` · `OOM_IN_LOG`(굵은 3종은 2.7.4). 진단류: `SNAPSHOT_TRUNCATED` · `FILE_READ_INCOMPLETE` · `MEMBER_NO_DUMP` · `SNAPSHOT_LIMIT_HIT` · `THREAD_LIMIT_HIT` · `LINES_UNPARSED` · `HEAP_DERIVED` · `NO_TIMESTAMP` · `SINGLE_SNAPSHOT` · `NO_LOCK_OWNER_INFO` · `RESTART_BETWEEN_SNAPSHOTS` · `RULE_FAILED` · `RESULT_TRIMMED`. 시그니처(유휴·수신 대기·소켓 읽기·연결·DNS·커넥션 풀 종류·JDBC·HTTP 클라이언트·요청 풀 이름·락 종류·호출 지점)는 `ThreadDumpRules` 한 곳. 발동 조건·근거·원인 연결은 아래 "소견 점검·고도화" 절.
- **결과 JSON 은 사전화돼 있다**(`ThreadDumpResult`, schema 1): `tracks`(스냅샷을 가로지르는 스레드) → `stacks`(프레임 인덱스 열, 저장 깊이 64) → `frames`, 이름은 `names`. 소견·락·교착·정체·CPU·스택 묶음이 스레드 **인덱스**를 참조한다. 스레드 3,000개 × 스냅샷 4개가 약 0.7MB.
- **실패 코드**(`status=ERROR`, `error_code`, `error_message="CODE: 설명"`): `NOT_THREAD_DUMP` · `UNSUPPORTED_FORMAT` · `EMPTY` · `TOO_LARGE` · `TIMEOUT` · `CANCELLED` · `FILE_MISSING` · `IO_ERROR` · `OUT_OF_MEMORY` · `INTERNAL` · `INTERRUPTED`. 결과 화면 `thread-dump-analyze.js` 의 `ERROR_HINTS` 가 코드별 안내문을 갖는다(`ThreadDumpTemplateSmokeTest` 가 목록을 대조 — 코드를 추가하면 두 곳을 함께 고칠 것).
- **실패시키지 않고 보완하는 것**은 `diagnostics` 에 세고 화면·PDF 의 "파싱 진단" 카드로 보인다: 잘린 스냅샷·스레드, 해석 못 한 줄(건수 + 앞 20건), 잘라 낸 긴 줄, 치환한 깨진 문자, 지운 제어문자, 상한 도달, 시각 줄 없음, 미지의 상태·락 줄, 건너뛴 규칙.
- **로그:** `[ThreadDump] action=upload|upload-rejected reason=|register|adopt|release|forget-moved|analyze-submit|analyze-done|analyze-failed code=|cancel|delete|server-name|recover-interrupted|rule-failed … by=`. PDF 는 `[ThreadDump-PDF] action=pdf-download|pdf-preview result=OK|FAIL file= size= elapsed= by=`(힙·코어와 같은 형식), AI 는 `[ThreadDump-AI]`. 사용자가 일으킨 결과(취소·형식 불일치)는 WARN, 조사해야 하는 것(`IO_ERROR`·`OUT_OF_MEMORY`·`INTERNAL`)은 스택과 함께 ERROR. 비동기 분석의 수행자는 요청 스레드에서 잡아 `runAnalysis` 로 넘긴다.
- **API 오류 본문은 `{success:false, code, error}`.** 컨트롤러의 `Exception` 핸들러는 스프링이 상태를 정해 둔 예외(`ErrorResponse`)의 상태를 지키고, DB 장애는 전역 계약(503 + `Retry-After` + `DB_UNAVAILABLE`)을 그대로 낸다.
- **리포트:** `ThreadDumpPdfReportService.buildPrintModel` → `Map` 을 PDF(`PdfReportService.renderPdf`)와 HTML 미리보기가 공유한다. 템플릿 `thread-dump/analyze-print.html`. 행은 맵이고 표시 문자열·막대 폭·상한 초과 건수까지 Java 에서 계산한다. 요약 문서라 스레드 전체 표는 넣지 않는다. 엔드포인트 `GET /thread-dump/analyze/{fn}/print-pdf?mode=download|inline` · `…/print-html`.
- **AI:** `ThreadDumpPromptBuilder.build`(≤12,000자, 형식 지시는 잘리지 않게 끝에 다시 붙인다) → `callLlmAnalysis(prompt, TD_SYSTEM_PROMPT)` → `ThreadDumpAiResponseNormalizer` → `ai_insights` 키 `__threaddump__:{fn}`. 덤프 원문은 보내지 않는다(소견·교착 사슬·상위 락·정체 스레드·상위 스택 묶음만). 재분석하면 AI 해석을 지운다(새 결과와 맞지 않는다). 응답 키: `summary` · `rootCause` · `recommendations` · `severity` · `severityDesc` · `codeAdvice`.
- **화면:** `templates/thread-dump/{index,analyze}.html` + `static/js/thread-dump-{index,analyze}.js` + `static/css/thread-dump.css`(로드 순서 common → core-dump → gc-log → thread-dump, 레이아웃·모달·KPI·소견은 `.gcl-*` 재사용). 결과는 페이지에 싣지 않고 `GET /api/thread-dump/{fn}/result` 로 받는다(저장본 그대로 — 파싱에 실패하면 재분석을 안내). 탭 5개: 요약 / 락·정체 / 스레드 / AI 분석 / 리포트. 스레드 표는 `TableGrid` detach 다.
- **테스트 204건**(영역별 내역은 `TEST_INVENTORY.md`), 픽스처는 `src/test/resources/threaddump/`(이 호스트의 JDK 8·21 로 받은 실측 덤프 — 데모 프로그램: 모니터 교착 2 + synchronized 경합 6 + ReentrantLock 경합 3 + 풀 유휴 4·활성 2 + busy loop + Object.wait). ⚠ 픽스처는 `.txt`/`.gz` 로만 둘 것 — `.gitignore` 가 `*.log`·`*.out` 을 무시한다. 운영 덤프는 넣지 않는다(저장소가 public).

## 힙 덤프 연계 · 이어 붙이기 (2026-11-26 v2.7.1)

세 기능이다. 사용자 결정: 힙 → 스레드는 **힙 결과 카드 + 전용 화면**, 스레드 덤프 ↔ 힙 덤프는 **수동 연결만**(후보를 보여 줄 뿐 자동으로 잇지 않는다), 이어 붙이기는 **수동 선택 + 업로드 직후 제안**(자동으로 묶지 않는다).

- **힙 덤프의 스레드 분석(스레드 덤프 없이)** — `service/HeapThreadService` + `parser/threaddump/HeapThreadExtractor`. 입력은 힙 분석이 이미 남긴 MAT 산출물이다: 결과 디렉토리의 `<base>.threads`(스택·지역 변수) + `<base>_System_Overview.zip`(없으면 `_Leak_Suspects.zip`)의 `pages/Thread_Overview*.html`(이름·daemon·우선순위·State value·Retained Heap). 둘을 **객체 주소**로 잇고, 스레드 덤프 텍스트(`Full thread dump Java VM (heap dump derived):`)로 바꿔 **같은 분석기**로 돌린다(`ThreadDumpEngine.analyze(…, heapDerived=true)`). 그래서 **이미 분석된 힙 덤프에도 재분석 없이** 적용되고, 결과는 DB 에 두지 않고 그때그때 만든다(LRU 4개, 산출물 크기·mtime·덤프 시각이 바뀌면 다시 만든다). 수백 개 스레드면 수십 ms.
  - 결과 `meta.source="heap"`·`meta.heapFilename`, 트랙마다 `hr`(Retained Heap)·`hl`(지역 변수 최대 Retained)·`hc`(스레드 클래스). 진단: `heapNotAliveThreads`(뺀 NEW·TERMINATED) · `heapThreadsWithoutStack` · `heapThreadsWithoutState`.
  - 소견 `HEAP_DERIVED`(Info)가 "스냅샷 비교·CPU·synchronized 락 관계는 없다" 를 알리고, `NO_TIMESTAMP`·`SINGLE_SNAPSHOT` 은 내지 않는다(당연한 것이라 소음이다).
  - 화면: 힙 결과(`analyze.html`) 헤더의 **Threads 칩**(연결된 스레드 덤프 + "스레드 분석" 링크)과 Thread Overview 패널 맨 위 **요약 카드**(`static/js/heap-threads-card.js` → `GET /api/thread-dump/heap/{fn}/summary`). 상세는 스레드 덤프 결과 화면을 **힙 모드**로 쓴다(`GET /thread-dump/heap/{fn}` — `THD_MODE='heap'`, 분석·재분석·삭제·폴링 없음, '힙 점유' 열·카드). API `/api/thread-dump/heap/{fn}/{result,summary,ai-analyze,ai-insight}`, 리포트 `/thread-dump/heap/{fn}/{print-html,print-pdf}`(파일명 `<base>-thread-report.pdf`). AI 키 `__heapthreads__:{fn}`.
  - 실패 코드: `HEAP_NOT_FOUND`(404) · `HEAP_NOT_ANALYZED`(409) · `HEAP_THREADS_UNAVAILABLE`(404 — 산출물 없음, 힙 재분석 안내) · `IO_ERROR`·`INTERNAL`(500). 요약 API 는 실패해도 200 + `available=false` 로 답한다(카드가 사유만 보인다).
  - 힙 AI(`/api/llm/analyze`)에는 `HeapAiApiController.threadPromptSection` 이 **스레드 상태 요약(≤900자) + 연결된 스레드 덤프 소견(≤900자)** 을 GC 섹션과 같은 자리(첫 `\n== ` 앞)에 끼운다. 실패하면 빈 문자열 — 힙 AI 를 막지 않는다.
- **스레드 덤프 ↔ 힙 덤프 수동 연결** — `thread_dump_analysis.linked_heap_filename`·`linked_at`·`linked_by`. 결과 화면 헤더의 '힙 덤프' 칩 → 후보 모달(`GET /api/thread-dump/{fn}/heap-candidates`) → 선택(`POST …/heap-link {heapFilename}`, 빈 값이면 해제). 분석이 끝난(`SUCCESS`) 힙 덤프만 연결된다.
  - 후보 점수(정렬용일 뿐): 같은 서버 +1 · 덤프 시각이 스냅샷 구간 ±`threaddump.match.tolerance-min`(기본 10분) 안 +1 · 스레드 이름 50% 이상 일치 +1(점수가 있는 상위 10개만 힙 산출물을 읽어 계산).

## 소견 점검 · 고도화 (2026-11-27 v2.7.4)

현행 규칙을 코드로 점검해 틀리게 말하던 것 8건·놓치던 것 8건을 고치고, 소견마다 **근거 줄**과 **원인 연결**을 붙였다. 원칙은 그대로다 — 덤프 글자로 확인되는 것만 말하고, 세어서 나온 추정에는 "의심" 을 붙인다.

- **활동 분류는 한 곳**(`ThreadDumpAnalyzer.activityOf` — `Activity` 12종). 정체 분류(`stuckCategory`)·풀 분해·I/O 묶음·원인 연결이 같은 분류를 쓴다. 판정 순서가 규칙이다:
  - BLOCKED → (풀의 synchronized borrow 면 `CONN_POOL_WAIT`) `LOCK_WAIT`
  - RUNNABLE → `LISTEN` → `CONNECT_WAIT`(연결·DNS) → `DB_WAIT`(소켓 읽기+JDBC) → `REMOTE_WAIT`(소켓 읽기+HTTP 클라이언트) → `REQUEST_READ` → `SOCKET_WAIT` → `RUNNING`
  - WAITING/TIMED → `CONN_POOL_WAIT` → `IDLE` → `LOCK_WAIT`(ReentrantLock park) → `SLEEP` / `WAIT_OTHER`
  - **`REQUEST_READ`(요청 수신 대기)** = RMI 연결 스레드가 다음 호출을 기다리는 읽기(`TCPTransport.handleMessages` 가 상위 12프레임 안), 또는 요청 처리 풀 스레드가 서블릿(`HttpServlet.service`)·필터(`.doFilter(`) 프레임 없이 소켓을 읽는 것. **유휴로 센다**(풀 유휴 수·`Track.idle`·정체 제외·"작업 중" 분모 제외).
  - `Stuck.category` 문자열(`blocked`·`lock-wait`·`pool-wait`·`io`·`running`·`sleeping`·`waiting`)은 바꾸지 않았다 — 화면 `CATEGORY_KO`·PDF `categoryLabel` 이 이 값을 쓴다.
- **결과 JSON 추가 필드**(schema 는 1 그대로, 전부 null 기본 — 옛 결과에는 키가 없다):
  - `Finding.basis`(근거 줄 ≤8) · `Finding.related`(이어진 소견 **코드**) · `verdict{headline, points[], codes[]}`(종합 진단) · `meta.ruleset`(=2).
  - ⚠ `basis`·`verdict` 에 스레드·스택 **인덱스를 넣지 말 것** — 코덱의 줄이기·재색인(`retainTracks`)은 `Finding.tracks` 만 고친다. 이름·주소·수치만 문장으로 넣는다.
  - `verdict` 는 기존 `diagnostics`(파싱 진단)와 헷갈리지 않게 지은 이름이다.
- **원인 연결**(`correlate` — 문제 규칙 뒤·`ruleDiagnostics` 앞, `runRule` 격리): 규칙이 남긴 `poolHits`·`lockHits` 로 대상을 찾아 겹침만 센다.
  - 풀 → 작업 중 스레드의 활동 분해(근거 첫 줄). 한 활동이 절반을 넘으면 그 소견과 잇는다(락 대기면 그 풀 스레드가 가장 많이 기다리는 락).
  - 락 → 소유·사슬 끝 스레드의 활동, 교착에 묶였는지.

- **옛 결과:** `meta.ruleset` 이 없으면 소견 카드 머리에 재분석 안내(`#thdRulesetNote` — 원본 파일이 있고 힙 모드가 아닐 때). 화면은 DB 원문 JSON 을 그대로 받으므로 JS 가 `(f.basis || [])` 로 방어한다. 일괄 재분석은 없다 — 파일마다 재분석해야 새 판정이 적용된다.
- **실측한 것 / 못 한 것:** 연결(`PlainSocketImpl.socketConnect`·`Net.connect0`·`NioSocketImpl.timedFinishConnect`)·DNS(`Inet4/6AddressImpl.lookupAllHostAddr`)·콘솔 락·JUL 락·RMI 대기 프레임은 이 호스트 JDK 8·21 데모 덤프로 확인했다. **WebLogic Muxer 와 연결당 스레드 방식 WAS(JEUS/WebtoB 등)의 요청 수신 대기는 실측 덤프가 없어 합성 텍스트로만 검증했다**(함정 91). `SOCKET_WAIT_CLUSTER` 의 묶음 기준(5)도 운영 덤프로 보정이 필요할 수 있다.

## 함정

72. **`Object.wait()` 중인 스레드도 `- locked <X>` 를 찍는다 — 같은 스택에 `waiting on <X>` 가 있으면 소유자가 아니다 (2026-11-26)** — `wait()` 는 모니터를 놓고 기다리는데 jstack 은 그 스레드가 과거에 잡았던 지점에 `locked` 를 그대로 출력한다. `locked` 만 보고 소유자를 정하면 **락을 놓고 쉬는 스레드를 범인으로 지목**하고, 그 스레드를 깨우려고 기다리는 스레드들과 묶여 가짜 경합·가짜 교착이 나온다. `ThreadDumpAnalyzer.buildLocks` 는 스레드마다 `waiting on` 주소 집합을 먼저 모으고 그 주소의 `locked` 는 건너뛴다. 대기 간선도 마찬가지로 가려야 한다 — `parking to wait for` 는 클래스가 `ReentrantLock`·`ReentrantReadWriteLock` 의 `Sync` 일 때만 락 경합이다(`ConditionObject`·`SynchronousQueue`·`CountDownLatch` 대기는 정상적인 대기다). j.u.c. 락의 소유자는 `Locked ownable synchronizers` 가 있을 때만 알 수 있으므로(`jstack -l`) 없으면 `owner=-1` + `NO_LOCK_OWNER_INFO` 로 알린다.

73. **`RUNNABLE` 은 CPU 를 쓴다는 뜻이 아니다 — 소켓 읽기·accept·select 는 RUNNABLE 로 찍힌다 (2026-11-26)** — JVM 은 네이티브 메서드 안에서 블로킹된 스레드를 RUNNABLE 로 보고한다. 그래서 ① "RUNNABLE 이 많다 = CPU 포화" 로 읽으면 안 되고, ② "같은 스택에 머문다 = 무한 루프" 도 아니다. Acceptor·Selector·Poller 는 평생 같은 스택이다. `ThreadDumpRules.traitsOf` 가 스택을 `listen`(정상 — 정체에서 제외) / `socketRead`(상대 응답 대기 — 분류 `io`) / 그 밖(분류 `running`)으로 가른다. 풀 밖 스레드의 `WAITING`·`sleep` 도 정체로 치지 않는다(스케줄러·타이머는 원래 그렇다). CPU 판정은 JDK 11+ 의 `cpu=` 누적값 **차이**로만 한다 — JDK 8 덤프에는 값이 없어 그 규칙이 돌지 않는다.

74. **스레드 동일성은 `#n`+`tid` 다 — 이름도, 파일 mtime 도, 재기동을 넘는 비교도 믿으면 안 된다 (2026-11-26)** — ① WebLogic 은 상태에 따라 이름을 바꾼다(`[ACTIVE]` → `[STUCK] ExecuteThread`). 이름을 키로 쓰면 같은 스레드가 둘로 갈린다. 풀 묶기(`ThreadDumpRules.stem`)만 이름을 쓰고 상태 접두를 뗀다. ② 서버 stdout 에는 여러 실행의 덤프가 쌓인다. `#1 main` 은 재기동 후에도 `#1 main` 이라 번호만 보면 서로 다른 JVM 의 스레드를 이어 붙여 "30분째 같은 스택" 을 만들어 낸다. VM 버전 줄이 바뀌거나 앞 스냅샷과 겹치는 식별자가 하나도 없으면 실행(run)을 나누고, 비교 규칙은 같은 실행 안에서만 돈다. ③ 타임스탬프 줄이 없을 때 파일 mtime 을 쓰지 말 것 — 업로드본의 mtime 은 업로드 시각이다(GC 로그 함정 67 과 같은 부류). 간격은 `elapsed=` 차이의 중앙값으로 추정하고(`intervalSource=elapsed`), 그것도 없으면 지속 시간을 스냅샷 개수로만 말한다. 구역 없는 시각 줄은 서버와 같은 구역으로 해석한다 — 다르면 간격만 맞고 절대 시각은 어긋난다.

75. **제어문자는 입구에서 지운다 — 스레드 이름·프레임에 섞인 0x1B·NUL 은 PDF·JSON·프롬프트를 제각각 다른 곳에서 깨뜨린다 (2026-11-26)** — 컬러 로그의 ANSI 이스케이프나 깨진 바이트가 덤프에 섞이는 일은 흔하다. 뒤쪽에서 각자 막으면 한 곳은 반드시 빠진다(특히 인쇄 템플릿은 XHTML 파서를 지나간다). `ThreadDumpEngine.LineReader` 가 읽는 자리에서 ANSI 시퀀스와 탭 외 C0 문자를 지우고(`strippedControlChars`), 깨진 UTF-8 은 U+FFFD 로 치환해 센다(`replacedChars`). 같은 리더가 **줄 버퍼 상한**도 지킨다 — `BufferedReader.readLine` 은 줄바꿈 없는 바이너리를 만나면 파일 전체를 한 줄로 쌓아 힙을 터뜨린다(GC 로그 엔진은 이 방어가 없다). 스레드 이름의 `<`·`&`·따옴표는 Thymeleaf `th:text` 가 이스케이프한다 — 인쇄 템플릿에 `th:utext` 를 쓰지 말 것.

76. **분석 실행기는 `Throwable` 을 잡아야 한다 — `Exception` 만 잡으면 OOM 한 번에 행이 영원히 "분석 중" 이다 (2026-11-26)** — `OutOfMemoryError`·`StackOverflowError` 는 `Exception` 이 아니다. 실행기에 맡긴 작업에서 나면 Future 가 조용히 삼키고, 상태를 ERROR 로 바꾸는 코드에 닿지 못한 채 **로그도 없이** `ANALYZING` 이 남는다(운영 힙이 `-Xmx512m` 라 실제로 날 수 있다). `ThreadDumpAnalyzerService` 는 네 겹으로 막는다: ① `runAnalysis` 가 `Throwable` 을 잡고(`OUT_OF_MEMORY`/`INTERNAL`) `fail()` 안의 저장 실패도 따로 감싼다 ② 대기 중(queued) 작업을 취소하면 `runAnalysis` 가 아예 돌지 않으므로 `cancel()` 이 직접 `CANCELLED` 를 쓴다 ③ 기동 직후 `recoverInterrupted()` 가 남은 `ANALYZING` 을 `INTERRUPTED` 로 돌린다 ④ `getStatus()` 가 "DB 는 분석 중인데 살아 있는 작업이 없다" 를 보고 고친다(제출과 같은 락에서 재확인 — 제출 도중을 고아로 오인하지 않게). 취소로 세워진 인터럽트 플래그는 실패를 기록하기 전에 내릴 것(`Thread.interrupted()`) — 남아 있으면 그 DB 저장이 실패한다. 같은 구멍이 `GcLogAnalyzerService.runAnalysis`(`catch (Exception)`, 기동 복구 없음)에 그대로 있다 — 이번 변경 범위 밖이라 손대지 않았다. 분석 규칙도 같은 원리로 격리한다: `ThreadDumpAnalyzer.runRule` 이 규칙 하나의 예외를 `RULE_FAILED` 로 남기고 다음 규칙으로 넘어간다(시간 초과·취소만 그대로 올린다).

77. **힙 덤프의 스레드 정보는 스레드 덤프가 아니다 — 상태는 MAT 표의 `State value` 비트에서, 이음은 이름으로만 (2026-11-26)** — MAT `.threads` 에는 이름·상태·락 줄이 없고 프레임은 JVM 시그니처 형식이다(`Lpkg/Cls;` → `HeapThreadExtractor.frame` 이 `pkg.Cls.method(File.java:N)` 로 바꾼다). 이름·daemon·상태는 Overview ZIP 의 Thread Overview 표에서 **헤더 이름으로 열을 찾아** 읽는다(열 순서는 MAT 버전마다 다르다). 상태는 JVMTI 비트(`ALIVE 0x1 · TERMINATED 0x2 · RUNNABLE 0x4 · WAITING 0x10/0x20 · SLEEPING 0x40 · IN_OBJECT_WAIT 0x100 · PARKED 0x200 · BLOCKED_ON_MONITOR_ENTER 0x400`)라 ALIVE 가 없거나 TERMINATED 인 스레드(시작 전·끝난 `Thread` 객체)는 **빼고 센다** — 넣으면 "스레드 수" 가 부풀고 풀 유휴 판정이 틀린다. 옛 MAT 결과처럼 `State value` 열이 없으면 상태를 지어내지 말고 UNKNOWN 으로 둔다(`heapThreadsWithoutState`). **synchronized 모니터의 소유 관계는 복원할 수 없다**(JDK 21 힙 덤프에는 MONITOR_USED 루트가 0개다) — 그래서 교착·락 경합 소견은 힙 모드에서 나오지 않는 게 정상이고, `HEAP_DERIVED` 소견이 이를 알린다. 스레드 덤프와 힙 덤프의 스레드를 이을 때 **주소·tid 로 잇지 말 것** — 힙의 주소는 `Thread` 객체 주소이고 jstack 의 `tid=` 는 네이티브 `JavaThread*` 라 서로 다르다. 이름으로 잇되 **양쪽에서 이름이 유일한 스레드만** 쓴다(풀 스레드가 아닌 `Thread-#`·같은 이름 스레드는 잘못 이어진다 — `HeapThreadService.Loaded.byName`·`ThreadDumpAnalyzerService.focusNames`). 두 덤프는 다른 순간이므로 화면·PDF·프롬프트에 "연결한 힙 덤프 기준" 과 시각 차(`gapSec`)를 함께 보인다.

78. **이어 붙인 결과는 대표 행에만 있다 — 묶음 정리는 참조만 끊고, 같은 이름의 새 파일은 옛 묶음·연결을 이어받지 않는다 (2026-11-26)** — 결과·AI 해석·요약 컬럼은 대표(`member_files` 가 있는 행)에 붙고 구성 파일 행은 `part_of` 만 갖는다. 재분석(`submitAnalysis`)은 저장된 구성 그대로 다시 읽는다 — 구성 파일이 디스크에서 사라졌으면 `FILE_MISSING` 이 **그 파일 이름을 담아** 실패한다(`ThreadDumpEngine.Source.of`). 구성 파일 삭제·저장소 이동·같은 이름 재등록 때 `detachFromGroup` 은 대표의 `member_files` 에서 그 이름만 빼고(2개 미만이 되면 묶음 표시를 지운다) **이미 만든 결과는 그대로 둔다**(다시 분석하면 남은 구성으로 한다). 대표가 사라지면 구성 파일들의 `part_of` 를 비운다. 어느 경우에도 **다른 파일 자체를 지우지 않는다**. `forgetAnalysis`(같은 이름의 다른 파일이 들어올 때)는 묶음·힙 연결 컬럼도 함께 비운다 — 안 비우면 새 파일이 옛 묶음의 대표 행세를 하거나 엉뚱한 힙 덤프와 이어진 채 보인다. 묶음 정리 실패는 삭제·이동을 막지 않는다(WARN `detach-group-failed`).

79. **409 는 전용 예외로만 낸다 — `IllegalStateException` 을 통째로 409 로 매핑하면 내부 오류 메시지가 사용자에게 샌다 (2026-11-26)** — `ThreadDumpApiController` 의 `Exception` 핸들러는 예상 못 한 예외를 500 + 일반 문구로 숨긴다(`ThreadDumpEndpointTest.errorContract` — `IllegalStateException("secret internal detail")` 가 새면 실패). "분석 중인 파일은 묶을 수 없다" 같은 상태 충돌은 `ThreadDumpAnalyzerService.BusyException` 으로 던지고 그것만 409 `CONFLICT` 로 매핑한다.

80. **템플릿의 모드 플래그는 `<html th:with>` 에서 한 번 boolean 으로 만든다 — `${!heapMode}` 는 변수가 없으면 SpEL 오류로 페이지가 중간에 끊긴다 (2026-11-26)** — `thread-dump/analyze.html` 은 스레드 덤프 모드와 힙 모드를 함께 그린다. 컨트롤러가 `heapMode` 를 넣지 않는 경로(기존 스모크 테스트·다른 화면에서 같은 템플릿 사용)에서 `!heapMode`·`fileExists and !heapMode` 가 null 을 만나 `TemplateProcessingException` 이 나고, 운영에서는 chunked 응답이 잘린 빈 화면으로 보인다(함정 23). `<html th:with="hm=${heapMode == true}">` 로 정규화하고 본문은 `${hm}` 만 쓴다.

90. **커넥션 풀 대기는 유휴 시그니처에도 맞는다 — 유휴 판정을 먼저 하면 풀이 커넥션 대기로 꽉 찬 것을 "전부 유휴" 로 읽는다 (2026-11-27)** — HikariCP 는 `ConcurrentBag.borrow` 안에서 `SynchronousQueue` 로 기다리는데, `SynchronousQueue` 는 스레드 풀이 일거리를 기다릴 때도 쓰여 유휴 목록에 있다. 2.7.3 까지는 `traitsOf` 가 `idle` 과 `connPoolWait` 를 따로 켜고 `isIdle`·`stuckCategory` 가 `idle` 을 먼저 봐서, 커넥션을 기다리는 요청 스레드가 **풀 유휴 수·화면의 '유휴' 태그에 들어가고 정체(`pool-wait`)·I/O 분모에서 빠졌다** — 요청 풀 200개가 전부 커넥션 대기여도 `POOL_NO_IDLE` 이 나지 않았다(테스트 주석은 "유휴가 아니다" 라고 적어 놓고 단언은 없었다). `traitsOf` 끝에서 `connPoolWait` 면 `idle=false` 로 내리고, `activityOf` 도 `CONN_POOL_WAIT` 를 `IDLE` 보다 먼저 본다. 같은 부류: 시그니처 목록을 늘릴 때는 **더 특정적인 판정이 일반 판정에 가려지지 않는지**(연결 대기 vs 소켓 읽기 — JDK 21 은 꼭대기가 둘 다 `sun.nio.ch.Net.poll` 이라 그 프레임은 어느 목록에도 넣지 않는다, DB 대기 vs 요청 수신 대기) 순서를 먼저 정할 것. `threadLink` 에 둘째 인자를 붙이면 안 되는 것도 같은 종류의 함정이다 — 여러 곳이 `.map(threadLink)` 로 불러 배열 인덱스가 스냅샷 번호로 들어간다(소견용은 `threadLinkAt`).

91. **종합 진단의 머리는 최고 등급 소견이어야 한다 · 실측하지 못한 WAS 패턴은 이름으로만 가른다 (2026-11-27)** — ① 처음에는 "이어진 소견이 있는 것 중 가장 심각한 것" 을 머리로 골랐더니, 교착(Critical, 이어진 소견 없음)과 락 경합(High, 이어진 소견 있음)이 함께 있는 덤프에서 **화면 배너가 교착을 제쳐 두고 락 경합을 말했다**. `buildVerdict` 는 최고 등급 소견들 안에서만 머리를 고르고, 그중 이어진 것이 없으면 `verdict` 를 만들지 않는다(배너·PDF 가 최상위 소견으로 대신). ② WebLogic Muxer(`ExecuteThread … for queue: 'weblogic.socket.Muxer'`)는 이름이 요청 풀 규칙에 맞고 바닥에 실행기 프레임(`weblogic.work.ExecuteThread.run`)도 있어 요청 처리 풀로 올라갔다 — 평생 같은 스택이고 서로의 락을 기다리는 모습이 정상인데 정체·유휴 없음 대상이 됐다. **프레임 이름은 버전마다 달라 이름으로만 가른다**(`ThreadDumpRules.isMuxerName` — `isWorkerStem`·`buildPools` 의 승격·`activityOf` 세 곳). 연결당 스레드 방식 WAS 의 유휴(서블릿·필터 진입 전 소켓 읽기)도 같은 이유로 "요청 처리 풀 + 서블릿·필터 프레임 없음" 이라는 구조 조건으로만 판정한다. **둘 다 실측 WebLogic·JEUS 덤프로는 확인하지 못했다** — 실측 덤프가 생기면 `ThreadDumpFindingInsightTest` 의 합성 케이스를 실측 프레임으로 바꾸고, 오탐·미탐이 보이면 조건을 고칠 것(필터가 아닌 밸브·인터셉터 단계에서 소켓을 읽는 WAS 는 유휴로 잘못 셀 수 있다).
